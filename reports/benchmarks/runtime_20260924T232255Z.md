## Findings and decision (2026-09-25)

All arms on GPU0 (300 W cap), same Q6_K file unless noted, Azure judge for golden.

| | llama.cpp b10068 (prod) | via llama-swap | Ollama 0.34.4, library q8_0 | Ollama, our Q6_K |
|---|---|---|---|---|
| Median real turn (conversation probe, router + reply) | 9.52 s | = direct | **4.64 s** | **4.53 s** |
| p90 turn | 14.68 s | = direct | 8.51 s | 8.60 s |
| Cached 3k-token prompt, 1 token | 1234 ms | 1232 ms | 241 ms | 241 ms |
| Generation | 55.2 tok/s | 55.3 tok/s | 54.6 tok/s | 60.0 tok/s |
| Cold start (first reply after unload) | resident | +5.5 s | 5.5 s | 5.1 s |
| VRAM | 13.0 GB | 13.0 GB | 14.2 GB | 11.1 GB (no vision) |
| Golden, extended average | 3.994 | not rerun (same engine) | 4.042 | 3.958 |
| Probe checks (routing, restraint, voice, no-dash, compliance) | all 100% | | all 100% | all 100% |
| Refusal rate | 0% | | 4%* | 0% |
| Needle recall to 28k | 100% | | 100% | 100% |
| Vision (3 synthetic images) | works in prod** | | 3/3 | not possible |

\* The one flagged reply (to a slur-based prompt about the group) was an in-character roast,
not a refusal; the detector matched a phrase inside it. \** The harness's llama.cpp vision request
failed (0.0 s responses); llama.cpp vision is exercised by production every day.

**Why llama.cpp is slow here.** Gemma 4 uses sliding-window attention. llama.cpp's default
reduced SWA cache has to be rebuilt on a cache hit: ~1.2 s on a 3k-token prompt even though
`prompt_n` reports 1 re-evaluated token. It is not fixed in the latest build (b11151, same
1.23 s). `--swa-full` removes it (27 ms) but takes **22.8 GB** at `-c 32768`, which cannot share
GPU1 with the app's own 2.5–4.3 GB. Ollama gets 241 ms in 11–14 GB. A turn is two calls
(router, then reply), which is why the whole turn halves.

**llama-swap costs nothing warm** (within 3 ms) and ~5.5 s on the first request after its model
was evicted.

**Other measurements.** bge-m3: 105 ms per query on GPU vs 881 ms on CPU, and a turn encodes
several times, so it stays on the GPU. Whisper large-v3: 2.1 GB loaded, back to 0.3 GB (CUDA
context) after unload, reload 2.5–5.4 s, 20.6 s of audio transcribed in 0.7 s; the 30 min idle
unload stays. Pi journal: ~14 MB per week (82 msgs/day mean, 5.9 images/day), so 7-day
retention is negligible on the 240 GB SSD.

**Decision.** Kaya is served by **Ollama with the library `gemma4:12b-it-q8_0`** (vision needs
the library model; our GGUF with a separate mmproj imports text-only), as a model inside the
llama-swap broker so there is still one queue and one set of GPU rules. It meets every
condition of the plan's rule: golden within ±0.07, no probe regression, faster turns, cold start
no worse, vision working. Ollama's gemma4 thinks by default; every chat-style call must send
`think: false` or the thinking consumes the whole token budget and the reply comes back empty.
Raw `/api/generate` with our own template does not trigger it.
