# The GPU PC's power schedule

The PC wakes at 07:00 every day and **turns itself off at night once nothing is
running**. From 2026-10-05 to 2026-10-15 it was turned off by hand only, because
a fixed 23:00 shutdown kept taking it down at bad moments; it was left on all
night instead. Now `power.shutdown` lists the **earliest** time per evening
(23:00, 02:00 after Friday and Saturday) and the shutdown waits for idle (below).
It can still be turned off by hand at any time. The single source of truth is
`config.yaml` → `power`. What acts on it is generated from that block, never
edited by hand:

| Where | What | Generated by |
|---|---|---|
| PC | `kaya-going-down.service` → `/usr/local/sbin/kaya-going-down.sh` at every poweroff | `sudo deploy/power/install.sh` |
| PC | `kaya-shutdown.timer` → `kaya-shutdown.sh` at the earliest time of each evening | `sudo deploy/power/install.sh` |
| PC | `kaya-power-listener.service` → `/usr/local/sbin/kaya-power-listener` on port 8099 (the Pi's `/homelaboff` trigger) | `sudo deploy/power/install.sh` |
| PC | `kaya-shutdown-manual.service` → `kaya-shutdown.sh --manual`, started by the listener | `sudo deploy/power/install.sh` |
| PC | `kaya-early-wake.timer` → `kaya-shutdown.sh --after-early-wake`, 10 min after boot | `sudo deploy/power/install.sh` |
| Pi | `pc-wake.timer` (Wake-on-LAN, 5 min before wake time) | `scripts/deploy_pi.sh` |
| Pi | the gateway's offline reply ("volto às 07:00") | read at gateway start |

After changing `power:` in `config.yaml`, rerun both of those.

## Turning the PC off

Any way works: the desktop menu, the power button, `systemctl poweroff`. As
long as the network and the containers are still up, `kaya-going-down.service`
(its `ExecStop`) does three things:

1. Waits up to 60 s for WhatsApp replies the bot has already accepted
   (`POWER_REPLY_WAIT_SECONDS`).
2. Tells the Pi gateway the PC is going down. Its offline reply then says
   *"Estou desligado agora. Volto amanhã às 07:00…"* until the PC is back. A PC
   that just disappears (a crash, a power cut) gets the fault line, *"Estou em
   baixo…"*, after 90 s.
3. Sets an **RTC alarm** for the next wake, as a backup to the Pi's Wake-on-LAN.

A reboot is skipped (`reboot.target` queued), since the PC is back within a
minute. Every run is in the journal of the boot that ended:
`journalctl -b -1 -u kaya-going-down`. Dry run:
`sudo /usr/local/sbin/kaya-going-down.sh --dry-run`.

**Never add `docker stop` to this.** A container stopped explicitly stays stopped
after the reboot, so the stack would not come back at 07:00. A stop started by the
daemon during poweroff does come back, and so does `restart: unless-stopped`.

## Turning it off from WhatsApp (`/homelaboff`)

The owner DMs the bot `/homelaboff` (and `/homelabon` to wake it). The gateway
(`src/gateway/homelab.py`) handles the DM and never lets it reach Kaya; it talks
to a listener on the PC. The flow:

1. The gateway asks the listener `GET /power/status`, which runs
   `kaya-shutdown.sh --report`: what is running (CI job, Qwen run, job container,
   idea-pipeline container, busy GPU) plus notes (a kernel without its nvidia
   module, `.stay-on`, Kaya's in-flight replies).
2. It shows that to the owner and asks for confirmation. `yes` starts
   `kaya-shutdown-manual.service`; `no` and a 5-minute expiry keep the PC on.
3. The manual mode waits until the PC is idle, sending a WhatsApp update every
   30 minutes and giving up after 12 hours (`POWER_MANUAL_MAX_WAIT_MINUTES`).
   It uses the same busy checks as the scheduled mode, except `.stay-on` is
   ignored — he asked for it — and a busy GPU counts as Kaya's while she is
   finishing a reply.
4. When idle it warns on the desktop, waits `POWER_WARN_SECONDS`, then does the
   shared last steps: Kaya's replies, the going-down notice, the RTC alarm, and a
   plain `systemctl poweroff`. No `docker stop`.

`cancel` (DM or the listener's `POST /power/cancel`) stops the wait while it is
still waiting; once it has switched to "stopping" it is too late. The listener
authenticates the Pi by IP allowlist (`POWER_ALLOWED_IPS`) and the relay token,
and its only job is to start `kaya-shutdown-manual.service` — it never powers
anything off itself. Logs:
`journalctl -u kaya-power-listener -u kaya-shutdown-manual`.

While Kaya has replies in flight, GPU load counts as hers and does not hold the
shutdown, except on the dev card (`POWER_DEV_GPU_UUID`, GPU0 by UUID): a bench or a
`qcode` session there still does. `install.sh` adds keys a newer release introduced
to an existing `/etc/kaya-power.env` and leaves the other lines alone.

## A Claude session from WhatsApp (`/homelabrc`)

The owner DMs `/homelabrc` (a session in `~/Desktop`) or `/homelabrc home` (in `~`);
`/homelabrc stop [home]` ends it. The gateway calls the same listener, with the same
IP and token checks:

- `POST /rc/start?dir=home|desktop` runs, as `POWER_USER` and inside that user's
  systemd manager (linger keeps it up), never as root:
  `systemd-run --machine=gustavo@ --user --unit=claude-rc-<dir> --collect
  claude remote-control --spawn=session --name homelab-<dir>`.
  It reads the unit's journal for up to 20 s and answers with the
  `https://claude.ai/code/session_…` link, which the gateway sends back.
  The directory is fixed by `dir`; a path is never taken from the request.
- One session per directory: a second start gets 409 ("already running").
  `--spawn=session` exits when that session ends, and nothing restarts it or
  starts one at boot.
- `POST /rc/stop?dir=…` stops the unit; `GET /rc/status` lists what is running.
- `POWER_RC_CLAUDE` overrides the claude binary (default `~/.local/bin/claude`).
- The directory must already be trusted by Claude Code (run `claude` there once):
  with no terminal there is nobody to answer the trust prompt, and the session dies.

Logs: `journalctl --user -u claude-rc-home -u claude-rc-desktop`.

## Approving sudo from the phone

A sudo with no terminal (a Claude Code or Remote Control session) asks the owner on
WhatsApp before it asks for a password. `install.sh` installs
`/usr/local/sbin/kaya-sudo-approve` (`kaya_sudo_approve.py`) and puts this line before
`@include common-auth` in `/etc/pam.d/sudo`:

    auth [success=done default=ignore] pam_exec.so quiet /usr/local/sbin/kaya-sudo-approve

1. The script runs as root, only for `POWER_USER`, only for sudo, and only when
   `PAM_TTY` is not a terminal. At the keyboard, sudo asks for the password as before.
2. It posts the command line, its directory and the processes that started it
   (`bash ← claude`) to the gateway's `POST /pc/sudo/request`, with the relay token.
3. The gateway DMs the owner the command and a 4-digit code. `yes 1234` allows that one
   sudo, and `no 1234` refuses it. A plain `yes` or `no` sent as a reply quoting the
   request works too. The request expires after 10 minutes (2 until 2026-10-15,
   too short to catch on the phone).
4. The script polls `GET /pc/sudo/<id>` and exits 0 only on `approved`.

`default=ignore` means anything else falls through to the normal password (askpass/zenity
or nothing). That includes a refusal, a timeout, an unreachable Pi, or a missing script, so
a broken approval path can never lock sudo out. Your password is never stored anywhere.
Each approval covers one sudo call, plus sudo's own 15-minute cache for the same parent
process, so batch root steps into one command. `install.sh --uninstall` removes the line.

## The nightly shutdown waits for idle

`power.shutdown` lists the earliest time of each evening (`sun: "23:00"`,
`fri: "02:00"`: a time before noon belongs to the night after that evening).
`install.sh` turns it into `kaya-shutdown.timer` → `kaya-shutdown.sh`, which
postpones while the PC is in use:

- `~/.stay-on` exists. The idea pipeline holds it while any idea has work left,
  so the PC goes off after the pipeline finishes, not between two of its jobs;
- the keyboard or mouse was used in the last 30 minutes (GNOME's idle monitor);
- a Claude Code session wrote to its transcript in the last 30 minutes
  (`~/.claude/projects/*/*.jsonl`): a Remote Control session from the phone
  touches no keyboard;
- a CI job, a `qwen-impl` run, or a job container (`kaya-train`, `kaya-data`,
  `kaya-infer`, `kaya-llama-bench`, `kaya-sim`) is running;
- a GPU is at 30% utilisation or more on two readings 5 s apart.

It checks again every 10 minutes and stops retrying 1 hour before the next wake,
leaving the PC on for the day (`POWER_RETRY_MINUTES`, `POWER_IDLE_MINUTES`,
`POWER_CLAUDE_IDLE_MINUTES`, `POWER_STOP_BEFORE_WAKE_MINUTES` in
`/etc/kaya-power.env` override the defaults). Once idle it warns on the desktop
for 2 minutes, then powers off; `kaya-going-down.service` does the rest. Its
decisions are in `journalctl -u kaya-shutdown`. `touch ~/.stay-on` keeps the PC
up for a night; remove it afterwards. To go back to turning it off by hand, set
`power.shutdown: {}` and rerun `install.sh`, which removes the timer.

## Waking early for the idea pipeline

The idea pipeline (a sibling project) waits on Claude's quota at night. When the
quota runs out it writes a wake request — `~/.wake-at`, the epoch seconds on the
first line (override the path with `POWER_WAKE_REQUEST_FILE` in
`/etc/kaya-power.env`) — and the nightly shutdown honours it: the PC wakes at
the reset time instead of 07:00.

A request is honoured only when it is inside the night window (the PC is
scheduled off at `now`), after `now`, and at least
`power.early_wake_margin_minutes` (60) before the next scheduled wake — the PC
still gives up that long before 07:00. The check is one function,
`PowerSchedule.early_wake` in `src/gateway/schedule.py`, used by both machines
so they cannot disagree.

The flow:

1. `kaya-shutdown.sh`, once idle, asks the schedule for the early wake. When it
   honours one, it writes `/var/lib/kaya-power/early-wake` (the marker of the
   early wake this boot followed) and sends `{"wake_at": <epoch>}` with
   `/pc/going-down`. `kaya-going-down.sh` reads the same marker and sends the
   same time, whichever of the two runs last.
2. The gateway (`src/gateway/early_wake.py`) keeps the accepted time in the
   journal's meta table, so a restart does not lose it, and when it is due it
   writes the same `pc-wake.request` file `/homelabon` writes, so the existing
   `pc-wake-request.path` unit sends the Wake-on-LAN.
3. The PC boots, and ten minutes later `kaya-early-wake.timer` runs
   `kaya-shutdown.sh --after-early-wake`: it consumes the marker and runs the
   same postponing loop, so the PC powers off again once idle — and honours a
   new request when it does, so the cycle repeats. By then the day has usually
   started, in which case it just leaves the PC on.

`/homelaboff` (the manual mode) never honours a request: the owner asked for the
PC off now, and it clears a stale marker.

The RTC alarm is set to the early time as a backup, but the board's 06:55
Resume-by-Alarm wins over `rtcwake` (see Waking up), so the Pi's packet is the
real early wake. If the Pi misses it, the PC wakes at the normal time.

**Known side effect:** labwatch's `boot_source`
(`labwatch/collectors/power_schedule.py` in the telemetry repo) labels any boot
between midnight and 06:50 "early", so an early wake raises the "PC woke outside
its schedule" alert until labwatch learns about it (a separate PR there).

Its decisions are in `journalctl -u kaya-early-wake` and
`journalctl -u kaya-shutdown`.

## Waking up

- **Primary:** the Pi sends a magic packet at 06:55 and retries every minute for
  10 minutes until the PC answers (`deploy/pi/pc-wake.sh`). To wake it by hand,
  run `pi5 wake-pc`.
- **Backup:** the BIOS alarm (below), and the RTC alarm `kaya-going-down` sets at poweroff.

Both depend on **BIOS settings that software cannot change**. The board is a
**Gigabyte X570 AORUS PRO** (BIOS F39; `cat /sys/class/dmi/id/board_name`; the
hostname's "MS-7C91" is not the board). Under **Settings → Platform Power**:

| Setting | Value | Why |
|---|---|---|
| **ErP** | **Disabled** | When enabled, it disables Resume by Alarm, Wake on LAN and every other wake source (manual, Platform Power) |
| **Wake on LAN** | **Enabled** | Default. The onboard NIC is an Intel I211 (`igb`), which supports magic-packet wake |
| **Resume by Alarm** | **Enabled**, every day, **06:55:00** | The board's own alarm time wins over `rtcwake`, and the RTC keeps UTC: 06:55 UTC is 07:55 in summer and 06:55 in winter, never before the Pi's packet |
| AC BACK | Memory (optional) | After a power cut, the PC returns to the state it was in |

The RTC alarm does not survive removing AC power (manual), so it is only the
backup. The Pi's magic packet is the primary wake.

**Resume by Alarm woke the PC at 01:00.** From 2026-09-29 to 2026-10-10 this
guide said "Enabled, any time". Every night the PC was off it then booted at
01:00 WEST, which is 00:00 UTC (the RTC runs on UTC), the BIOS's default alarm
time. The shutdown script had set the alarm for 07:00 each time
(`journalctl -u kaya-going-down`), so the board used its own time, not the OS
one. The early boot also exhausted the locked GNOME keyring before anyone logged
in. The setting was fixed in the BIOS on 2026-10-11. labwatch now alerts on
WhatsApp when the PC boots before 06:50 without Wake-on-LAN or the RTC
(`health.pc_wake_by`).

**The BIOS alarm time is what fires, not the OS one.** With Resume by Alarm left
at 0:00:00, the PC shut down at 23:32 on 2026-09-28 and powered itself on at
01:00 (00:00 UTC). `/proc/driver/rtc` read `alrm_time 00:00:00` although
`rtcwake` had set 06:00 UTC. Shutdowns after 01:00 (Friday and Saturday nights)
hide it, because that day's alarm has already passed. labwatch flags a boot
before 06:50 that follows a scheduled poweroff ("PC woke outside its schedule")
and sends a WhatsApp.

`install.sh` also makes Wake-on-LAN persistent in NetworkManager
(`802-3-ethernet.wake-on-lan magic`).

## Installing

```bash
sudo deploy/power/install.sh              # then set KAYA_RELAY_TOKEN in /etc/kaya-power.env
systemctl is-active kaya-going-down.service   # active; no kaya-shutdown.timer while power.shutdown is empty
sudo deploy/power/install.sh --uninstall
```

Test once, with nobody depending on the bot:

- **RTC (best effort):** `sudo rtcwake -m off -s 300` should power off and come back in 5 minutes.
- **Wake-on-LAN:** `sudo systemctl poweroff`, then `pi5 wake-pc`.

## Kernel updates are manual

`install.sh` keeps `linux-*` out of unattended-upgrades. On 2026-09-25 they
installed kernel 7.0.0-34 without its nvidia module, and the next boot had no
GPU driver: Docker could not start the GPU containers and the bot went silent.
Upgrade kernels at the machine with `sudo apt full-upgrade` (which brings
`linux-modules-nvidia-595-open-*` for the new kernel), then reboot.

Two guards stay in place:

- `kaya-shutdown.sh` skips the night if the kernel booted next has no nvidia
  module.
- `kaya-boot-check.service` tells the Pi gateway when a boot has no driver, so
  users get "Estou em baixo…" instead of silence. It never loads the module
  itself: loading it under a desktop that booted without it froze the PC.
